# Бизнес-требования: Tariff Analyzer

## 1. Цель продукта
Tariff Analyzer проверяет корректность тарификации SMS-платформы и правильность классификации SMS-сообщений по типам трафика.

Приложение должно помогать пользователю отвечать на два бизнес-вопроса:
- корректно ли представитель SMS-платформы рассчитал стоимость сообщений;
- корректные ли типы трафика были присвоены SMS-сообщениям.

Проект находится в активной разработке. Текущая цель - MVP, сфокусированный на генерации конфигурации, валидации конфигурации, обработке большого файла сообщений и воспроизводимом CSV-результате.

## 2. Основной сценарий пользователя
Первое использование:
1. Пользователь запускает приложение.
2. Пользователь загружает `message_templates.csv`.
3. Пользователь загружает `tariff.csv`.
4. Приложение разбирает оба файла и генерирует JSON-конфигурацию.
5. JSON-конфигурация сохраняется в папке с исполняемым файлом.
6. Пользователь может открыть и отредактировать JSON-конфигурацию в любом текстовом редакторе.
7. Приложение валидирует сгенерированную конфигурацию и показывает ошибки, если они есть.

Стандартное использование:
1. Пользователь запускает приложение.
2. Приложение автоматически загружает JSON-конфигурацию из папки с исполняемым файлом.
3. Приложение валидирует конфигурацию при запуске.
4. Если конфигурация некорректна, приложение сообщает об ошибках с деталями, достаточными для ручного исправления.
5. Пользователь загружает большой CSV-файл сообщений, структурно аналогичный `sample_files/full_msg.csv`.
6. Приложение обрабатывает файл.
7. Приложение записывает итоговый CSV с расчетными колонками в конце.
8. Если в настройках включен debug-режим, приложение дополнительно записывает UTF-8 копию результата и отдельный лог обработки.
9. После успешной генерации файлов приложение показывает dashboard текущего запуска с финансовой сводкой, качеством классификации и диагностикой обработки, если его отображение включено в настройках. По умолчанию dashboard включен. Если отображение выключено, приложение оставляет пользователя на обычном экране анализа и показывает пути к созданным файлам.

## 3. Входные файлы

### `message_templates.csv`
Файл содержит SMS-шаблоны и допустимые типы трафика.

Текущий пример: `sample_files/message_templates.csv`

Известные свойства:
- кодировка: Windows-1251;
- разделитель: `;`;
- структура ожидается аналогичной примеру;
- файл содержит текст SMS-шаблона, имя отправителя и соответствия типов трафика по операторам.

Ожидаемые колонки из примера:
- `ID`
- `Текст шаблона`
- `Имя отправителя`
- `Типы трафика`

Значение `Типы трафика` содержит одно или несколько соответствий в формате, похожем на:
`СМС:mts:Сервисный, СМС:megafon:Сервисный`

Сгенерированная конфигурация должна сохранять достаточно информации, чтобы определить корректный тип трафика сообщения по шаблону, имени отправителя и оператору.

### `tariff.csv`
Файл содержит тарифные данные.

Текущий пример: `sample_files/tariff.csv`

Известные свойства:
- кодировка: Windows-1251;
- разделитель: `;`;
- структура ожидается аналогичной примеру.

Ожидаемые колонки из примера:
- `Описание`
- `Количество`
- `Цена (руб. с НДС)`
- `Стоимость (руб. с НДС)`

Сгенерированная конфигурация должна нормализовать строки тарифа в машиночитаемые тарифные правила:
- имя отправителя;
- оператор;
- тип сообщения или тип трафика;
- цена с НДС;
- границы тарифного диапазона или диапазон количества;
- алиасы, необходимые для сопоставления значений из файла сообщений.

Тарифы могут зависеть от количества сообщений. Например, первые 5000 сообщений могут иметь одну цену, а следующие сообщения - другую. Модель конфигурации должна поддерживать такую ступенчатую тарификацию.

### CSV-файл сообщений
Пользователь выбирает файл сообщений через интерфейс.

Полный пример: `sample_files/full_msg.csv`

Маленький пример структуры: `sample_files/messages.csv`

Известные свойства:
- полный файл может быть больше 1 ГБ;
- структура примера считается репрезентативной для реальных файлов;
- приложение не должно считать, что реальный файл физически находится в `sample_files/`.

Ожидаемые колонки из примера:
- `Наименование учётной записи`
- `Идентификатор родительской транзакции`
- `Идентификатор транзакции`
- `Номер телефона`
- `Имя отправителя`
- `Текст SMS`
- `Дата отправки`
- `Дата доставки`
- `Кол-во недоставленных частей`
- `Кол-во доставленных частей`
- `Ошибка`
- `Тип канала доставки`
- `Тип сообщения`
- `Тип трафика`
- `Оператор/направление`

## 4. JSON-конфигурация
Приложение должно генерировать человекочитаемую JSON-конфигурацию. JSON выбран как основной формат, потому что он структурирован и при этом может быть быстро отредактирован вручную в текстовом редакторе.

Конфигурация должна сохраняться в папке с исполняемым файлом и автоматически загружаться при запуске приложения.

Конфигурация должна содержать минимум два логических раздела:
- шаблоны сообщений;
- тарифные правила.

### Конфигурация шаблонов
Каждый объект шаблона должен содержать:
- стабильный идентификатор шаблона из `message_templates.csv`;
- текст шаблона;
- имя отправителя;
- нормализованное представление для сопоставления, если оно нужно реализации;
- соответствия операторов и типов трафика;
- исходную информацию, полезную для диагностики.

Порядок шаблонов в конфигурации имеет бизнес-значение. Если одному сообщению соответствует несколько шаблонов, используется первый подходящий шаблон в порядке JSON-конфигурации.

### Конфигурация тарифов
Каждое тарифное правило должно содержать:
- имя отправителя или ключ сопоставления отправителя;
- оператор или алиас оператора;
- тип трафика или тип сообщения, необходимый для расчета цены;
- значение цены;
- границы тарифного диапазона или информацию о диапазоне;
- исходную информацию, полезную для диагностики.

Модель должна поддерживать тарифы, зависящие от количества сообщений, где порядковый номер сообщения внутри группы тарификации определяет применимую цену.

Текущая согласованная трактовка для MVP:
- группа тарификации определяется полями, которые требуются тарифному правилу, минимум именем отправителя, оператором и типом трафика;
- порядковый номер сообщения рассчитывается во время обработки входного файла внутри применимой группы тарификации;
- порядковый номер используется для выбора тарифного диапазона.

Уточнение для реализации MVP обработки сообщений:
- единица тарификации - одна строка CSV-файла сообщений;
- поля `Кол-во доставленных частей` и `Кол-во недоставленных частей` не изменяют количество тарифицируемых единиц;
- тарифные правила `Пропуск sms-трафика` из текущего `tariff.csv` считаются глобальными и применяются по оператору и типу трафика без привязки к имени отправителя;
- тариф с оператором `all` используется как fallback только если не найден тариф для конкретного оператора и того же типа трафика;
- типы трафика сопоставляются строго по нормализованному тексту; например, `Идентификационный` не считается алиасом `Авторизационный`;
- несколько тарифных строк с одинаковыми оператором и типом без явного диапазона считаются последовательными диапазонами в порядке CSV.

Если позднее правила биллинга потребуют другой ключ группировки или специальный учет частей SMS, сначала нужно обновить этот документ и domain model.

## 5. Валидация конфигурации
Приложение валидирует конфигурацию при запуске и после генерации.

Обязательная валидация:
- синтаксические ошибки JSON;
- отсутствие обязательных верхнеуровневых разделов;
- отсутствие обязательных полей в шаблонах;
- отсутствие обязательных полей в тарифных правилах;
- некорректный синтаксис шаблона;
- неподдерживаемые операнды шаблонов;
- пустое или некорректное имя отправителя;
- пустое или некорректное соответствие оператора;
- пустой или некорректный тип трафика;
- некорректный формат цены;
- некорректные или пересекающиеся тарифные диапазоны, если диапазоны заданы явно.

Ошибки валидации должны указывать точное место, когда это возможно:
- строка и колонка для синтаксических ошибок JSON;
- JSON path или аналогичное местоположение объекта для семантических ошибок;
- номер строки исходного CSV, если ошибка связана со сгенерированными данными.

UI должен показывать результаты валидации так, чтобы пользователь мог исправить конфигурацию вручную.

## 6. Сопоставление шаблонов
Корректный тип трафика определяется через сопоставление текста SMS с шаблонами из конфигурации.

Сопоставление должно соблюдать синтаксис SMS-шаблонов из `docs/template-syntax.md`.

Правила сопоставления:
- сравнивать текст SMS без учета регистра;
- игнорировать знаки препинания согласно правилам синтаксиса шаблонов;
- нормализовать пробелы перед сопоставлением;
- использовать имя отправителя из строки сообщения вместе с привязкой шаблона к отправителю;
- выбирать тип трафика для оператора сообщения из найденного шаблона;
- если найдено несколько шаблонов, использовать первый по порядку конфигурации;
- логировать все конфликты, где одному сообщению соответствует несколько шаблонов.

Оператор сообщения берется из `Оператор/направление`. Конфигурация должна поддерживать алиасы, если в разных источниках один оператор называется по-разному, например `tele2` и `t2`.

## 7. Правила обработки
Для каждой строки CSV-файла сообщений:
1. Прочитать строку без изменения исходных значений.
2. Определить текущий тип трафика из исходной колонки `Тип трафика`.
3. Найти все подходящие шаблоны для `Текст SMS` по правилам конфигурации.
4. Если шаблон не найден:
   - записать в `правильный тип` исходный `Тип трафика`;
   - записать в `определен ли шаблон` значение `не определен`;
   - записать в `есть ли конфликт шаблонов` значение `без конфликта`;
   - при включенном debug-режиме добавить запись в лог обработки;
   - рассчитать цену по исходному типу трафика.
5. Если найден один шаблон:
   - записать в `правильный тип` значение из найденного шаблона и соответствия оператора;
   - записать в `определен ли шаблон` значение `определен`;
   - записать в `есть ли конфликт шаблонов` значение `без конфликта`.
6. Если найдено несколько шаблонов:
   - использовать первый шаблон по порядку конфигурации;
   - записать в `правильный тип` значение из выбранного шаблона и соответствия оператора;
   - записать в `определен ли шаблон` значение `определен`;
   - записать в `есть ли конфликт шаблонов` значение `конфликт`;
   - при включенном debug-режиме добавить в лог идентификаторы совпавших шаблонов.
7. Рассчитать `стоимость по текущему типу` по исходному `Тип трафика`.
8. Рассчитать `стоимость по правильному типу` по рассчитанному `правильный тип`.
9. Рассчитать `наличие расхождение типа` только по факту отличия исходного `Тип трафика` от `правильный тип`.
10. Если при обработке строки возникли диагностируемые проблемы, записать их в колонку `ошибки обработки`, а при включенном debug-режиме также в отдельный лог обработки.

## 8. Расчет цены
Расчет цены использует тарифные правила из конфигурации.

Обязательные входные данные для поиска тарифа:
- имя отправителя из `Имя отправителя`;
- оператор из `Оператор/направление`;
- тип трафика, для которого рассчитывается цена;
- порядковый номер сообщения внутри применимой группы тарификации;
- тарифные диапазоны из конфигурации.

`стоимость по текущему типу`:
- использовать исходное значение `Тип трафика` из входной строки;
- определить применимую группу тарификации и порядковый номер сообщения;
- выбрать подходящий тарифный диапазон;
- записать цену из конфигурации.

`стоимость по правильному типу`:
- сначала определить `правильный тип`;
- определить применимую группу тарификации и порядковый номер сообщения для правильного типа;
- выбрать подходящий тарифный диапазон;
- записать цену из конфигурации.

Если тарифное правило не найдено, приложение должно добавить запись в лог и записать в расчетную колонку явное пустое или ошибочное значение. Конкретное значение должно быть единым во всем приложении и зафиксировано при реализации.

## 9. Выходной CSV
Выходной файл должен быть идентичен исходному CSV-файлу сообщений, кроме добавленных расчетных колонок.

Требования:
- сохранить все исходные строки;
- сохранить исходный порядок строк;
- сохранить исходные названия колонок;
- сохранить исходные значения;
- добавить расчетные колонки в конец;
- сохранить разделитель, сейчас `;`;
- сохранить файл в той же кодировке, что и входной файл;
- при включенном debug-режиме дополнительно сохранить копию итогового CSV в UTF-8 с суффиксом `_utf8` в имени файла;
- сохранить правила CSV-экранирования для значений в кавычках.

Обязательные добавленные колонки:
- `стоимость по текущему типу`
- `правильный тип`
- `стоимость по правильному типу`
- `наличие расхождение типа`
- `определен ли шаблон`
- `есть ли конфликт шаблонов`
- `ошибки обработки`

Допустимые значения:
- `определен ли шаблон`: `определен`, `не определен`
- `есть ли конфликт шаблонов`: `без конфликта`, `конфликт`

Для `наличие расхождение типа` нужно использовать единое бинарное представление. Конкретные значения нужно финализировать при реализации, например `да` / `нет`.

Для MVP используется `да` / `нет`.

Если тариф не найден, соответствующая колонка стоимости остается пустой, а причина записывается в `ошибки обработки` и лог. Если шаблон не найден или найденный шаблон не содержит соответствие для оператора, в `правильный тип` записывается исходный `Тип трафика`.

## 10. Лог обработки
Каждый запуск обработки в debug-режиме должен создавать отдельный файл лога. При выключенном debug-режиме лог обработки не создается; диагностика строк по-прежнему сохраняется в колонке `ошибки обработки` основного CSV.

Лог должен содержать:
- ошибки валидации конфигурации, если обработка была запущена с некорректной конфигурацией;
- строки, где шаблон не найден;
- строки, где найдено несколько шаблонов;
- строки, где не найдено соответствие типа трафика для оператора;
- строки, где не найдено тарифное правило;
- номер строки из CSV-файла сообщений;
- имя отправителя;
- оператор;
- исходный тип трафика;
- рассчитанный правильный тип трафика, если он доступен;
- идентификаторы найденных шаблонов, если они доступны;
- диагностическое сообщение.

Лог нужен для последующей отладки, ручной корректировки шаблонов и ручной корректировки тарифов.

## 11. Требования к производительности
Полный файл сообщений может быть больше 1 ГБ.

Требования к реализации:
- обрабатывать сообщения потоково;
- не загружать весь файл в память;
- записывать выходной CSV инкрементально;
- показывать прогресс обработки в UI;
- поддерживать отмену длительной обработки;
- держать потребление памяти ограниченным размером конфигурации и небольшими буферами;
- избегать работы на каждой строке, которая линейно зависит от полного списка шаблонов, если можно ввести индекс без изменения результата.

Корректность важнее преждевременной оптимизации, но архитектура не должна блокировать потоковую обработку.

## 12. MVP и будущие функции
MVP должен включать:
- импорт `message_templates.csv` и `tariff.csv` при первом использовании;
- генерацию JSON-конфигурации;
- автоматическую загрузку конфигурации;
- валидацию конфигурации;
- обработку большого CSV-файла сообщений;
- итоговый CSV с расчетными колонками;
- основной CSV в Windows-1251; UTF-8 копию и лог обработки при включенном debug-режиме.
- настраиваемый dashboard результата текущего запуска, включенный по умолчанию.

Dashboard результата текущего запуска включает:
- суммарную стоимость по исходным типам оператора;
- суммарную стоимость по рассчитанным правильным типам;
- разницу стоимости;
- сводка по количеству расхождений типов;
- отчет по неопределенным сообщениям;
- отчет по конфликтам шаблонов;
- отчет по отсутствующим тарифным правилам;
- покрытие расчета стоимости и определения правильного типа;
- основные переходы между исходным и правильным типами;
- операторов с наибольшей абсолютной разницей стоимости.

История запусков, восстановление dashboard после перезапуска, фильтры, временные графики, drill-down до отдельных SMS и сравнение запусков не входят в MVP.

## 13. Правила расчета dashboard
Dashboard рассчитывается потоково в том же проходе, в котором формируется итоговый CSV. Повторное чтение входного или выходного файла не требуется. Память ограничивается агрегатами по операторам, типам трафика и категориям проблем.

Настройка отображения dashboard влияет только на UI. Даже если dashboard скрыт, его агрегаты продолжают рассчитываться, а обработка сообщений, формирование CSV и debug-файлов выполняются без изменений.

Финансовые показатели:
- стоимость по исходным типам равна сумме найденных цен `стоимость по текущему типу`;
- стоимость по правильным типам равна сумме найденных цен `стоимость по правильному типу`;
- рядом с каждой суммой показывается количество строк с найденной ценой;
- разница равна сумме `стоимость по текущему типу - стоимость по правильному типу` только для строк, где найдены обе цены;
- положительная разница означает потенциальную переплату, отрицательная - потенциальную недоплату;
- арифметика выполняется точно, без чисел с плавающей точкой; в UI рубли показываются с двумя знаками после запятой;
- если тариф отсутствует, строка не добавляется в соответствующую сумму и снижает покрытие расчета.

Проблемы обработки классифицируются так:
- `Error`: не найден тариф для текущего или правильного типа, поэтому финансовый расчет строки неполон;
- `Warning`: шаблон не найден, в шаблоне нет типа для оператора или найден конфликт шаблонов;
- SMS учитывается не более одного раза в количестве затронутых строк каждой severity;
- отдельные события по категориям считаются независимо, поэтому у одной SMS может быть несколько событий.

Покрытие определения правильного типа включает только строки, где найден шаблон и соответствие типа для оператора. Fallback на исходный тип сохраняет требования к выходному CSV, но не считается успешным определением правильного типа.
